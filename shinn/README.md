# SHINN — Phase 1: Project, Database, Prisma, Migrations, Seed

This is the Phase 1 scaffold only, per the locked implementation order.
It does **not** include auth, admin CRUD, product APIs, or the real
storefront yet — those are Phases 2–6. What's here is enough to prove the
one-database, one-source-of-truth foundation actually works before anything
is built on top of it.

## What's in this phase

- Fresh Next.js 14 (App Router) + TypeScript project
- Tailwind configured with the locked black/white/gray design tokens
  (light + dark mode via CSS variables in `styles/globals.css`)
- Full locked Prisma schema (`prisma/schema.prisma`) — `Product`,
  `ProductVariant`, `ProductImage`, `Brand`, `Category`, `User`, `Session`
- Hand-written init migration matching that schema, including the two
  raw-SQL constraints Prisma's DSL can't express (NULL-safe variant
  uniqueness, single-main-image guarantee) — **see the warning below**
- A server-only Prisma client singleton (`lib/prisma.ts`)
- A minimal dev seed (`prisma/seed.ts`) — 2 brands, 2 categories, 2
  products, variants, one image
- A placeholder home page that queries the database directly and displays
  the result, so you can visually confirm the DB connection works —this is
  **not** the real storefront

## ⚠️ Before you run this

The migration file in `prisma/migrations/00000000000000_init/` was
hand-written to match the schema, since it was authored without a live
database connection to generate it against. **Do not trust it blindly.**
Before relying on it:

```bash
# 1. Point DATABASE_URL at a throwaway/dev database first
# 2. Delete the hand-written migration folder, then regenerate for real:
rm -rf prisma/migrations
npx prisma migrate dev --name init

# 3. Open the generated migration.sql and manually re-add the two raw-SQL
#    constraints (they're clearly marked "Hand-added, NOT generated by
#    Prisma" in the original file) — Prisma will not recreate these on its
#    own since they're not expressible in schema.prisma.
```

Once you've done this once for real, future schema changes go through the
normal `npx prisma migrate dev` flow.

## Setup

```bash
npm install
cp .env.example .env
# edit .env — set DATABASE_URL to your Postgres instance

npx prisma generate
npx prisma migrate dev   # after regenerating the migration per the warning above
npm run seed

npm run dev
```

Open `http://localhost:3000` — you should see "Database connection: OK"
with brand/product counts matching the seed data.

## Phase 1 exit criteria (confirm before moving to Phase 2)

- [ ] `npm run dev` boots with no errors
- [ ] Home page shows real counts from the database (not 0, not an error
      silently swallowed — if the DB is unreachable this page should throw
      visibly, per architecture rule 14)
- [ ] `npx prisma studio` lets you browse the seeded Brand/Product/Variant/
      Image rows directly
- [ ] Re-running `npm run seed` doesn't create duplicates (idempotent via
      `upsert`)
- [ ] Attempting to insert a second `isMain: true` image for the same
      product via Prisma Studio fails with a unique constraint violation
      (proves the partial index is live)

Once all of these hold, proceed to Phase 2 (authentication, admin
authorization, admin layout).
